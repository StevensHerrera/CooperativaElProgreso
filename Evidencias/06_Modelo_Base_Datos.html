3. Relaciones

  • Un asociado puede tener cero o muchos movimientos.
  • Un usuario puede registrar muchos movimientos.
  • Cada movimiento tiene un único tipo: depósito o retiro.
  • Una TRM puede ser utilizada en muchas consultas.
  • Un asociado puede tener muchas consultas de conversión.

4. Propuesta SQL

CREATE TABLE asociados (
  id UUID PRIMARY KEY,
  numero_documento VARCHAR(30) NOT NULL UNIQUE,
  nombre_completo VARCHAR(150) NOT NULL,
  telefono VARCHAR(30), direccion VARCHAR(200),
  fecha_registro TIMESTAMP NOT NULL,
  estado VARCHAR(20) NOT NULL DEFAULT 'ACTIVO'
);

CREATE TABLE movimientos (
  id UUID PRIMARY KEY,
  asociado_id UUID NOT NULL REFERENCES asociados(id),
  usuario_id UUID REFERENCES usuarios(id),
  tipo_id INT NOT NULL REFERENCES tipos_movimiento(id),
  monto DECIMAL(18,2) NOT NULL CHECK (monto > 0),
  comision DECIMAL(18,2) NOT NULL DEFAULT 0,
  fecha TIMESTAMP NOT NULL
);

5. Decisiones técnicas

  • El saldo no se almacena como columna; se calcula sumando depósitos y restando retiros, igual que en la aplicación actual.
  • Los movimientos no deben actualizarse ni eliminarse para conservar trazabilidad.
  • El documento del asociado es único.
  • Las llaves foráneas garantizan que no existan movimientos sin asociado.
  • Los índices recomendados son documento, fecha y asociado_id.
